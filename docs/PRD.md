## 1. 產品摘要

### 1.1 一句話定位

**Kunsu 是 AI Agent 在無法繼續工作時，用來取得人類決策的強制決策收件匣。**

（2026-10-13 起為公開產品，給所有用 AI Agent 工作的人；內容只留在使用者自己的電腦，見 §31。）

它不是通知中心或任務管理器，桌面端也不是聊天軟體。它只承接「AI 必須得到人的回答，否則工作無法安全
繼續」的 actionable question，以及使用者透過 Claude／Codex 排程交給 AI 督導的承諾 check-in，並持續
把問題帶回使用者眼前，直到問題正式結案。

### 1.2 核心問題

使用者很容易忽略 AI 訊息、關閉終端機或忘記回到對話。結果不是少看一則通知，而是整條
Agent 工作流卡死、決策上下文流失，甚至在不知道風險的情況下停擺。

一般通知失敗的原因：

- 通知容易被掃掉，沒有「必須處理」的產品語意。
- 問題分散在 Claude、Claude Code、Cursor、終端機與其他 Agent 中。
- 被關閉的提醒通常不會可靠地回來。
- 使用者回來時，原始問題、選項、證據與執行後果已經分散或遺失。

### 1.3 產品承諾

只要 AI 提出一個仍有效、仍需要人回答的問題，Kunsu 就會：

1. 將問題集中保存並立即開始 15 分鐘處理週期。
2. 讓倒數狀態在同一套 Agent 視覺上可理解。
3. 在剩餘 3 分鐘時清楚警告即將強制詢問。
4. 在時間到且環境安全時開啟全螢幕強制詢問介面。
5. 若使用者關閉但沒有回答，重新開始新的 15 分鐘週期。
6. 持續循環，直到回答、來源取消、被新題取代或合法到期。

「15 分鐘內強迫詢問」代表系統會在期限到達時主動把問題帶回來；它不宣稱能物理上強迫
使用者在第 15 分鐘完成作答。

### 1.4 核心原則：AI 當你最嚴厲的父親

Claude、ChatGPT／Codex 這類通用 AI 產品，基於商業與安全理由，產品設計上不可能強迫使用者做事：
它們等你回來、尊重你忽略。結果「AI 判斷需要你做的事」最後全部落回你的自制力。

Kunsu 是這件事的擴充：**它是你的 AI 長官，像最嚴厲的父親。** 只要 AI 判定需要你的決定，或你自己
透過排程交給 AI 的承諾到期，Kunsu 就不讓你假裝沒看見，直到你正式回應。

嚴厲有邊界，這些邊界本身也是產品的一部分：

- **嚴厲是逼你面對與回應，不是越權。** 它不替你作答、不代你授權、不自動執行預設選項。
- **嚴厲不讓你出糗。** 分享螢幕、錄影、會議與全螢幕展示時延後呈現，責任照樣累積。
- **勿擾是你有意識設定的時間盒，不是逃生門。** 最長 24 小時，題目與倒數照常保存，結束立即恢復。
- **答案要回到發問的那段對話。** 你回應後，AI 必須在原本那段 Claude／Codex 對話接著做，並把結果與
  回饋交代回來（§20），而不是在你看不到的地方另起爐灶。

## 2. 產品原則

1. **未回答不等於已處理。** 關閉、最小化、切換視窗與 app 重啟都不能把問題變成完成。
2. **強制詢問是產品本體。** 它不是額外通知功能，而是 Agent 等待人類決策時的可靠協定。
3. **一次只要求一個明確決定。** 全螢幕介面不變成 dashboard 或聊天串。
4. **打斷必須有理由。** 只接收會阻塞 Agent、需要核准或存在實質風險的 actionable question；
   FYI、進度播報與一般通知不進入 Kunsu。
5. **安全守門高於倒數。** 螢幕分享、錄影、會議、系統勿擾等情境不得彈出蓋板；逾時問題
   保持待強制，守門解除後立即恢復。
6. **內容可動態，介面不可失控。** Agent 可提供 Markdown、安全 HTML 與選項；需要圖表或任何視覺化時，
   可依 Claude Artifact 模式寫 React／HTML 畫布，但畫布只在沙盒中執行（無網路、無 Kunsu 權限、不能送出），
   題目、選項、送出與錢參數永遠由 Kunsu 原生呈現（2026-10-08 修訂，§24）。
7. **狀態可恢復、事件可追溯。** 重新開機、sleep/wake、來源重送與網路中斷都不能讓問題
   靜默消失或意外獲得新的寬限期。
8. **答案是唯一正常出口。** 除了來源取消、supersede 或合法 expiry，未回答問題必須回來。
9. **勿擾只延後呈現，不延後責任。** 使用者可啟用最長 24 小時的勿擾模式；期間完全不顯示
   系統通知、浮動膠囊或強制 overlay，但題目、倒數與稽核仍持續，結束後立即恢復。
10. **嚴厲而不越權。** Kunsu 強迫的是面對與回應（§1.4），永遠不替使用者作答、授權或執行。
11. **答案回到原對話。** 回答優先交還給發問的那段對話接續工作；只有確定無法接續時才另開新對話，並
    保留原對話連結（Target，§20）。
12. **強制介面永不擋死使用者。** 蓋板只能在內容可操作時出現，Esc 與關閉永遠有效；呈現失敗時改走
    主視窗，題目保持強制資格（Target，§22）。

## 3. 使用者與 Jobs to be Done

### 3.1 主要使用者

- 同時使用 Claude、Claude Code、Cursor 或自動化 Agent 的單一 macOS 使用者。
- 工作中會離開終端機或切換大量上下文，但仍需要保留最終決策權的人。
- 需要核准執行方向、風險、內容、發佈或其他不可由 AI 自行推定事項的人。

### 3.2 核心工作

- 當 Agent 卡住時，我要在不回頭翻對話的情況下理解問題並快速回答。
- 當我暫時忽略問題時，我要確定它稍後一定會再次出現，而不是永遠失蹤。
- 當問題涉及風險或執行後果時，我要看到足夠上下文，並留下可查證的決策紀錄。
- 當我正在分享螢幕、錄影或開會時，我要確定私人問題不會突然覆蓋畫面。
- 當有多個 Agent 等待時，我要依序處理，不被多個蓋板同時轟炸。

### 3.3 非使用者與非用途

- 多人團隊工單系統。
- 桌面端的即時聊天與長篇 Agent 對話（手機 App 可檢視與接續 Claude／Codex 對話，見 §30）。
- 一般通知、FYI、成功訊息或背景進度。
- 排程引擎、第二套資料真相或雲端同步服務（手機中轉站只轉送端對端加密封包、不存內容，見 §30）。
- 讓 Agent 繞過既有核准／金流安全通道的捷徑。

## 4. 產品架構與三個 Surface

三個 surface 是同一個問題狀態的連續呈現，不是三套產品。

### 4.1 Application（實體應用程式）

用途：管理決策收件匣、歷史、Agent 連線與產品設定。

核心能力：

- Onboarding：選擇 Claude、Claude Code、Cursor 或「其他」。
- Claude 與 Claude Code 為必須支援的第一級整合。
- 「其他」提供可複製／一鍵安裝的標準提示詞或 MCP 接法。
- 顯示待決、已回答、已取消、已取代、已過期與失敗的問題。
- 顯示每題來源、建立時間、當前 15 分鐘週期、回答回執與事件歷程。
- 提供 kill switch、安靜時段、整合狀態與診斷資訊。
- 提供可設定最長 24 小時的勿擾模式，清楚顯示結束時間並可提前結束。
- 無待決問題時仍可從 macOS menu bar 開啟應用程式。
- **Target：**「督導」頁依排程列出每次 check-in 的回應與 AI 回饋（§21）；回執顯示答案交付到哪段
  對話並可一鍵打開原對話（§20）。

### 4.2 Decision Capsule（任務提醒膠囊）

用途：在不霸佔畫面的情況下，持續表示「仍有 Agent 等待回答」。

> **Target（§19）：** 膠囊將改為貼齊螢幕邊緣的純黑「邊緣瀏海」，可沿四邊拖曳並停在角落成 L 形，
> hover 沿邊延長並播放題目跑馬燈。§19 交付後取代本節「固定 44 px、hover 不改變」的規則；交付前
> 本節仍是 Current。

Current 行為：

- 只有存在 actionable pending question 時才顯示。
- 固定 44 px 高，不因 hover、文字或 tooltip 改變幾何。
- 不顯示 hover tooltip，也不需要 hover 動畫。
- 可拖曳到螢幕邊界任一點；放開時平移至最近邊界，接近角落則吸附角落。
- 點擊開啟 overlay；拖曳不誤觸點擊。
- 顯示最精簡的等待狀態與題目數。倒數圓環可在 orb 周圍使用同一進度，維持跨 surface
  的視覺連續性。
- 無待決問題時隱藏，但 menu bar 入口永遠存在。

### 4.3 Decision Overlay（全螢幕強制詢問介面）

用途：把一個需要人類決定的問題變成唯一、清楚且可完成的當前工作。

目標行為：

- 無邊框、左右分割。左側是 Agent 粒子圖像與倒數；右側是題目、上下文、參考回答與輸入。
- 一次只呈現一題；多題可用左側進度與上一題／下一題快速跳轉。
- 問題、證據與參考回答支援 sanitized Markdown 與 safe HTML。
- 輸入框接受 Markdown 原文，不顯示重複的即時預覽。
- `Enter` 送出；`Shift+Enter` 換行。
- 輸入框為空時顯示「參考回答」；點文字填入，右側「直接送出」可快速回答。
- 一旦輸入框有文字，參考回答隱藏，避免搶焦點。
- 回答後保留在本次 flow 中供回看，但不可偷偷改寫 append-only 決策紀錄。
- 關閉未回答的強制介面不等於略過：必須開始新的 15 分鐘週期。
- **Target（§22）：** 精準覆蓋目標螢幕、內容就緒才出現、Esc 永遠有效、呈現失敗改走主視窗。

## 5. 核心需求：15 分鐘強制詢問循環（Current）

### 5.1 適用條件

進入循環的問題必須同時符合：

- 是 AI Agent 明確建立的 actionable question。
- 問題仍在有效期限內，且未被 answer、cancel 或 supersede。
- 需要人類回答才能安全繼續，不能由 Agent 自動推定。
- 通過 schema、來源權限、冪等與安全驗證。

一般 FYI、成功通知、背景狀態與不影響 Agent 繼續工作的詢問不得進入循環。

### 5.2 時間語意

每題建立或進入新的未解決週期時，保存：

- `cycle_started_at`：本輪起點，使用 UTC wall-clock timestamp。
- `warn_at = cycle_started_at + 12 minutes`。
- `force_at = cycle_started_at + 15 minutes`。
- `cycle_number`：從 1 開始，只有「使用者關閉未回答 overlay」才遞增。

倒數以持久化時間戳計算，不以容易因 sleep、重啟或 render pause 漂移的前端 interval 作為真相。

### 5.3 倒數圓環

左側 Agent 圖像外圍必須有一個完整圓環，表示本輪剩餘時間：

- 起始時為 100%，隨時間單調縮減，`force_at` 時為 0%。
- 圓環不旋轉、不閃爍，不改變圖像尺寸或版面位置。
- 進度以時間戳推導；切題、重繪、視窗重開不重設。
- 膠囊 orb 可呈現同一進度的緊湊版本，overlay 左側則呈現完整版本。
- `prefers-reduced-motion` 下保留靜態進度變化，不做粒子追逐或連續旋轉。
- 除顏色外，必須有可讀的剩餘分鐘文字／accessibility value，不能只靠紅綠色判斷。

### 5.4 三分鐘警告

當 `remaining <= 3 minutes` 且問題仍未解決：

- 右側題目區顯示明確警告：「3 分鐘後將開啟強制詢問」。
- 之後可顯示實際剩餘時間，例如「2:41 後將開啟強制詢問」。
- 警告使用 T0/danger 語意色，但不使用紫色或黃色漸層、不閃爍、不推動版面。
- 螢幕閱讀器只在跨入 3 分鐘門檻時公告一次，不每秒重複朗讀。

### 5.5 時間到達

當 wall clock 到達或超過 `force_at`：

1. 若所有強制守門均為綠色，開啟 overlay 並聚焦當前最早逾時的問題。
2. 若任一守門命中，不開啟 overlay，也不取消問題；問題進入 `force_deferred` 語意狀態。
3. 守門解除後，若問題仍有效且未回答，應在下一次狀態檢查立即開啟，不重新贈送 15 分鐘。
4. 開啟 overlay 本身不代表回答，也不能觸發 Agent 的預設執行。

### 5.6 關閉後重新計時

如果使用者在未正式回答時關閉 overlay：

- 當次關閉事件必須寫入 append-only event log。
- 該題立即開始新的完整 15 分鐘週期，`cycle_number += 1`。
- UI 回到膠囊；圓環由 100% 重新開始。
- 不因關閉次數自動降級、不自動歸檔，也沒有最大重試次數。
- 新週期同樣在剩餘 3 分鐘警告、時間到達後再次強制詢問。
- 循環持續到 terminal condition 成立。

「關閉」與「暫停提醒」不是兩個不同的免責入口；在 vNext 中，兩者對未回答問題都只代表開始
下一輪 15 分鐘週期。若未來要加入不同 snooze 時長，必須另開 PRD/BDD 變更，不能暗改。

### 5.7 結束條件

只有下列條件能停止循環：

- `answered`：使用者透過任何合法回答通道正式送出，且 app 已持久化 receipt。
- `cancelled`：原始 Agent 明確取消問題。
- `superseded`：同一決策被更新版本合法取代。
- `expired`：到達已宣告且合法的 expiry，依產品規則結案；不得用極短 expiry 規避強制詢問。

app 被關閉、overlay 被關閉、膠囊被拖動、來源暫時離線、UI render crash 都不是結束條件。

### 5.8 多題排隊

- 每題擁有獨立的持久化週期與倒數。
- 同一時間只顯示一個強制 overlay，不能疊加多個視窗。
- 強制排序預設為「已逾時最久者優先」，同時逾時則依風險與建立時間穩定排序。
- 使用者可在 overlay 內跳到其他題；切題不重設任何倒數。
- 回答當前題後，若仍有已逾時且 guards 全綠的題，flow 可無縫前往下一題，不需關閉再彈出。
- 蓋板開著時才到期的強制題接到這次作答的尾端（「第 N 題，共 M 題」跟著變多），不會被忽略；按「稍後再問」時它也
  一起開始新週期。蓋板收起後再檢查一次強制題，還有就立刻再呈現（2026-10-09 QA 第 2 輪，Ray 核准）。

### 5.9 冪等與生命週期恢復

- 同一 `question_id` 的 upsert/touch 不得重設倒數或 `cycle_number`。
- app restart 後從持久化 timestamp 還原；已逾時者在 guards 允許時立即強制。
- macOS sleep 不暫停 wall clock。喚醒時已逾時者依 guards 決定立即顯示或 deferred。
- 系統時鐘大幅倒退或前進時，持久化 timestamps 必須保持可查，並避免產生負進度或重複
  force event。
- 來源重送、網路重試與 UI remount 都不能生成第二個邏輯問題。

## 6. 強制守門與隱私

無論倒數是否到期，下列情境禁止顯示全螢幕 overlay：

- 正在螢幕分享或錄影。
- 攝影機或麥克風正在被會議情境使用。
- 前景應用程式處於全螢幕展示。
- macOS Focus／勿擾模式開啟。
- 位於 quiet hours。
- kill switch 尚未到期。

守門的產品語意是 **延後顯示，不是取消義務**。若題目在守門期間到期：

- 瀏海直接說是什麼擋住、什麼時候會跳出來（2026-10-09 Ray 核准，取代原本的「已到期，等待安全時機」）：
  分享螢幕→「時間到了，分享螢幕結束就跳出來」、鏡頭→「時間到了，鏡頭關掉就跳出來」、麥克風→「時間到了，麥克風關掉就跳出來」、
  前景全螢幕→「時間到了，離開全螢幕就跳出來」、勿擾（含全域快捷鍵暫停）→「時間到了，HH:MM 勿擾結束就跳出來」、安靜時段→「時間到了，HH:MM 安靜時段結束就跳出來」；同時命中多個只顯示第一個（依此順序），無障礙名稱列出全部；讀不到原因或沒有任何 guard
  命中（例如蓋板正要出現）時顯示「時間到了，馬上跳出來」。剛到期、還沒讀到原因前瀏海維持前一個文字，不先閃「馬上跳出來」。
  勿擾那一句目前看不到：Kunsu 勿擾時瀏海整個隱藏，系統專注模式偵測目前恆為 false；這句只在未來偵測系統專注模式時出現。
- 不公開問題內容於系統通知或可能被分享的畫面。
- 守門解除後立即恢復最早逾時題，不重新開始 15 分鐘。
- 守門期間不因 UI 沒出現而增加 `cycle_number`；只有使用者實際關閉未回答 overlay 才增加。

kill switch 是緊急免打擾功能，不是結案；到期後所有仍有效的逾時問題恢復強制資格。

### 6.1 勿擾模式（Current）

勿擾模式是使用者有意識地暫停 Kunsu 所有主動打擾的時間盒，不等於回答、取消、snooze 或
重設倒數。單次必須大於 0 且不得超過 24 小時；預設快捷選項為 1、4、8、24 小時，並提供
以 15 分鐘為步進的自訂時長。

啟用後直到 `ends_at`：

- 不顯示 macOS 系統通知、浮動膠囊或強制 overlay；已顯示的膠囊與 overlay 立即隱藏。
- menu bar icon 與主 Application 保持可用，讓使用者能主動查看待決題、看到「勿擾至 HH:mm」並
  提前結束；主動開啟主視窗不會自動開 overlay。
- 待決題照常建立、持久化、進入 warned／overdue；不增加 `cycle_number`、不執行答案、不重設
  `cycle_started_at`／`warn_at`／`force_at`。
- 勿擾狀態與結束時間必須持久化；app restart、sleep/wake 與 UI reload 不得提早解除或延長。
- 到期或提前結束後，若有已逾時題，下一次狀態檢查立即恢復最早逾時題；若尚未逾時，膠囊依
  正常規則恢復並沿用原倒數。

UI 以工具列單一狀態控制呈現：未啟用時顯示「勿擾模式」；啟用時顯示剩餘時間與結束時間，
展開可選快捷時長、自訂時長或「提前結束」。設定頁提供同一控制，menu bar 顯示唯讀狀態與
開始／結束入口。menu bar 清單必須顯示目前模式、精確剩餘時間、結束時間與待決數；未啟用時
可直接選 1／2／4／8／12／24 小時，啟用時可改選上述時間或提前結束，「更多時間…」開啟 app
設定頁的自訂分鐘控制。啟用與解除都必須立即回饋，但啟用成功不得再發一則系統通知破壞勿擾承諾。

AI Agent 可透過已驗證的本機 MCP 讀取、設定或解除勿擾模式。這些操作只改呈現 guard，絕不構成
任何題目的作答或授權；每次操作記錄 actor、requested duration、前後結束時間與時間戳。超過
24 小時、非正數或格式錯誤一律拒絕，AI 讀取結果必包含 active、ends_at、remaining_seconds。

## 7. 問題與回答內容模型

### 7.1 每題最小欄位

- 穩定 `question_id` 與 source/agent identity。
- 一句可獨立理解的 `question_line`。
- `body_md`：必要上下文、證據與風險。
- 零個或多個參考回答，每個包含 label、可選 detail、實際送出 value。
- 建立時間、deadline/expiry、風險 tier、default consequence。
- 可選 `visual_symbol`，受 bounded content grammar 限制。
- 目前狀態、週期時間戳、`cycle_number` 與 receipt。

### 7.2 內容安全

- Markdown 與 HTML 必須經 allowlist sanitizer。
- Markdown 內文中禁止 script、style、iframe、form、event handler、任意 class 與定位。
- **Current（§24）：** 唯一允許執行 agent 程式的地方是證據畫布：`sandbox="allow-scripts"` iframe、禁止所有網路與
  表單的 CSP、拿不到 IPC；畫布內任何操作都不能產生答案或批准。
- 外部連結與圖片遵守安全 URL policy；不能藉內容載入可執行資源。
- Agent 只能控制內容層次，不能控制 Kunsu 的字型、顏色、間距、按鈕與互動。

### 7.3 回答語意

- 參考回答只是建議，不得在使用者尚未送出時被視為答案。
- 直接送出與文字輸入都必須走同一條 receipt／回傳通道。
- 回答成功需顯示「已收到 → 已寫入決策帳本 → Agent 已接手／執行完成」等可驗證狀態。
- 回傳失敗不可把本地問題誤標為完成；應顯示可恢復錯誤並保留答案草稿／receipt。
- 涉及金流或高風險動作時，回答不等於繞過 prepare、簽章、TTL 或其他既有安全流程。
- **Target（§20）：** 「Agent 已接手」指的是發問的那段對話接手；回執標明交付路徑，並顯示 agent 以
  `ask_report` 回報的處理結果與 AI 回饋。

## 8. 整合與 Onboarding

### 8.1 必須支援

- Claude
- Claude Code

### 8.2 次要支援

- Cursor
- 其他支援標準提示詞、CLI hook、HTTP 或 MCP 的 Agent

### 8.3 Onboarding 成功條件

1. 使用者選擇 Agent。
2. app 顯示最少步驟的連線／安裝方式。
3. 完成一個 test question round-trip。
4. 使用者在 Kunsu 回答後，來源 Agent 能收到同一 `question_id` 的正式回答。
5. 整合失敗時顯示可執行診斷，不把原始 JSON、token 或秘密直接暴露在 UI。

### 8.4 原對話身分（Target，§20）

建題時必須記下「是哪一段對話在問」：主機（Claude App／Claude CLI／Codex App／Codex CLI）、對話 id、
Claude 桌面 session id、工作目錄、是否無人值守，以及排程身分。MCP 走 HTTP 看不到呼叫端環境，所以由
`kunsu ask` 從 agent 的環境自動補齊；不得讀取或保存任何跨 session 訊息 token 等秘密。

## 9. 關鍵使用流程

### 9.1 首次設定

開啟 app → 選 Claude／Claude Code／Cursor／其他 → 安裝整合 → 送出測試題 → 回答 → 驗證 Agent
收到 → 完成 onboarding。

### 9.2 正常作答

Agent 建題 → 膠囊出現、倒數開始 → 使用者在 15 分鐘內主動點開 → 閱讀上下文 → 選參考回答
或輸入 → 送出 → receipt 落盤 → Agent 接手 → 題目結案。

### 9.3 強制詢問

Agent 建題 → 12 分鐘後顯示三分鐘警告 → 15 分鐘到期 → guards 全綠 → 膠囊以墨水與粒子轉場
展開 overlay → 使用者回答 → 結案。

### 9.4 關閉但未回答

強制 overlay 顯示 → 使用者關閉 → dismissal event 落盤 → 膠囊保留 → 新 15 分鐘週期 →
三分鐘警告 → 再次強制 → 重複直到 terminal。

### 9.5 到期但正在分享螢幕

15 分鐘到期 → `screen_shared = true` → 不顯示 overlay、標記 deferred → 分享結束 → guards 全綠 →
立即開啟最早逾時題。

## 11. 非功能需求

### 11.1 可靠性

- 週期與答案狀態先持久化再更新 UI。
- force/dismiss/answer 事件具冪等鍵，crash recovery 不重複製造邏輯事件。
- app 不可因 overlay renderer 失敗而遺失問題；膠囊、menu bar 與 application 提供恢復路徑。

### 11.2 效能

- 膠囊與倒數閒置時不持續高 GPU/CPU 占用。
- 圓環更新允許視覺插值，但產品真相以 timestamp 計算。
- overlay 開啟動畫不能阻塞內容可讀性；動畫失敗時仍需顯示可操作介面。

### 11.3 Accessibility

- 全流程可只用鍵盤操作，焦點順序可預測，Esc/關閉行為有明確語意。
- 圓環提供文字與 accessibility value。
- 色彩對比符合 macOS 桌面工具的可讀性需求；狀態不只靠顏色。
- 尊重 `prefers-reduced-motion`，不因此移除時間與狀態回饋。

### 11.4 隱私與安全

- 本機優先，不建立多使用者雲端資料庫。
- 不在螢幕分享／錄影／會議時顯示問題內容。
- 診斷 log 不記錄 token、secret 或未遮蔽的敏感 body。
- Agent 內容永遠經 sanitizer，不能取得 UI 任意執行能力。

## 12. 成功指標與護欄指標

### 12.1 北極星指標

**需要人類回答的有效問題，最終取得可驗證回答的比例。**

### 12.2 核心指標

- 首輪 15 分鐘內回答率。
- 到第一次強制詢問前的回答率。
- 每題直到回答所需的平均／P95 `cycle_number`。
- 從建題到正式 receipt 的中位數與 P95 時間。
- Agent 成功接收回答的比例與延遲。
- 因 guards deferred 的問題數與 deferred 時長。
- app restart/crash 後成功恢復週期的比例。

### 12.3 護欄指標

- overlay 被立即關閉的比例。
- kill switch 使用率與持續時間。
- app quit／uninstall proxy、renderer crash、重複 force event。
- 被取消、supersede、expiry 的比例，以及是否存在濫用 expiry 逃避回答。
- 螢幕分享／會議期間誤顯 overlay 次數，目標必須為 0。
- 重複題、無法回答題與「這題不該問我」比例。

強制成功不能只看「彈了幾次」。若 cycle 數、kill switch 或 app quit 顯著上升，代表上游題目品質
或分級失敗，必須先修出題品質，而不是提高打斷強度。

## 13. 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 無限循環造成疲勞 | 使用者關 app 或停用產品 | 嚴格限制 actionable question、量測 cycle/kill switch、改善上游題目品質 |
| 與舊 T0 預算／snooze 模型衝突 | 實作與文件不一致 | 以本 PRD 為 vNext 目標，先更新 BDD/CONTRACT/INVARIANTS，再改狀態機 |
| 分享螢幕時洩漏問題 | 隱私與信任受損 | guards 為硬條件，overdue 只 deferred，測試逐一枚舉 |
| sleep/restart 偷偷重設倒數 | 強制承諾失效 | wall-clock timestamp 持久化，fake clock 測試 recovery |
| 同時大量問題轟炸 | 無法操作 | 單一 overlay queue、最早逾時優先、上游建題品質與配額 |
| 倒數動畫耗能 | 電池與效能下降 | timestamp 驅動、低頻更新、CSS/SVG 優先、視窗不可見時停止 render |
| 動畫或 WebGL 失敗導致不能答 | 核心流程中斷 | 動畫是 progressive enhancement，永遠保留靜態可操作 fallback |

## 14. 範圍外與紅線

本版本不做：

- 桌面端的聊天介面或長篇 conversation management。手機 App 可以檢視、接續與建立 Claude／Codex 對話（§30，2026-10-10 Ray 核准紅線後退），但決策題永遠用決策卡作答，不當成聊天訊息。
- 收 FYI 通知、一般進度或成功訊息。
- 第二條動錢通道或繞過既有 approval security。
- 重建排程引擎、把其他系統的資料真相搬進 app DB。
- Kongko 深度 API 綁定；只允許既定 deep link、publish webhook 與 MCP reconcile。
- 發佈等於啟用授權。
- 在螢幕分享、錄影、會議或全螢幕展示中顯示 overlay。
- 雲端保存對話、題目、答案、證據或任何內容；雲端只存帳號基本資料與裝置清單（§31.2）。手機 App 的中轉站只轉送端對端加密封包與無內容推播，不保存可讀內容（§30）。多使用者與對外公開產品已於 2026-10-13 由 Ray 核准（§31），不再是紅線；團隊協作（多人共用一個收件匣）仍不做。
- 由 Agent 注入任意 CSS、script、form 或自訂 UI。

排程督導（§21）依賴 Claude Routines 與 Codex automations，Kunsu 不新增任何排程時鐘；「回答延續原對話」
（§20）讓對話留在 Claude／Codex，桌面 Kunsu 內不出現聊天串（手機 App 例外見 §30，對話真相仍在 Claude／Codex）；目標正本留在 vault 或排程 prompt，不搬進 app DB。

## 15. vNext 遷移結果

截至 2026-08-05，vNext 已完成並安裝。舊的 T0-only、30 分鐘 warning、60 秒倒數、兩次 snooze
後降級與每日 forced budget 模型已停止控制強制詢問；既有資料會在 server 啟動時補齊週期欄位，
並以原始建立時間恢復牆鐘進度。

已上線模型如下：

| 面向 | Current |
|---|---|
| 首次強制週期 | 建題起 15 分鐘，剩 3 分鐘警告 |
| 關閉／稍後 | 未回答就開新 15 分鐘週期，次數不限 |

## 19. 邊緣瀏海（Current 第一版，2026-10-08；多螢幕拖曳轉移與點擊不啟用 app 待做）

把待決提醒做成從螢幕邊框長出來的純黑瀏海，像 MacBook 瀏海一樣和邊框融為一體。

- **存在規則不變：** 只有待決題時出現；零待決、勿擾時完全消失；menu bar 永遠是後備入口。
- **外觀：** 純黑、外側切齊螢幕實體邊緣，厚度固定；自由端圓角、與邊框交界有反向圓角，角落 L 形的
  內外轉折都是圓角，且所有圓角在移動中連續變化。
- **拖曳：** 永遠貼著某一邊。位置是沿螢幕周長的單一座標，拖曳時沿邊跟著游標；以速度預測與遲滯判斷
  使用者是否真的想換邊（單純往下拖不換邊，明確往右才轉到上方）；換邊與跨角都沿邊滑過去、經過 L 形，
  像貪食蛇一樣流動，永不瞬移。抓住哪裡，圖示就跟著游標沿那一臂移動多少；在角落 L 形兩臂重疊的那一格按下時，
  依開始拖曳的方向決定拖哪一臂（橫著拖就拖橫的那一臂）。
- **停靠：** 放開時靠近角落就停成 L 形（四個角都可以），否則停在邊上；位置跨重啟保留，記的是圖示那一端，
  所以重啟時文字長短不同，圖示也回到原位；螢幕用系統的螢幕識別記住，兩台同型號螢幕分得開。預設在左側、
  頂端在選單列下方，避免擋住 Apple 選單（選單列設成自動隱藏時也照標準選單列高度留位置）；停在上方角落時會蓋住
  部分選單列，這是使用者自己的選擇。
  解析度改變、睡眠喚醒、插拔螢幕後瀏海重新貼齊螢幕邊緣並回到記住的位置；記住的位置壞掉時回到預設位置。
  設定頁的「回到預設位置」讓瀏海立即回到預設位置；剛放開還沒寫進檔案（或寫檔失敗）時，螢幕重新貼合不會把它誤當成重設。
  瀏海只因三件事移動：使用者拖曳、文字長短改變、設定頁的「回到預設位置」。題數或狀態文字變長變短時，圖示那一端不動、只有尾端伸縮；
  但靜止時瀏海一定完整留在原本那條邊上（或停在角落的置中 L），文字變長會超出那條邊時整條往回移，尾端跟放開吸附一樣離螢幕邊 24 px，
  圖示只移動必要的距離；隱私狀態等其他變化不會讓它移動或中斷 hover。
- **內容：** 頭端是來源 AI 圖示，接著是一行字。預設「你有一則待處理通知」；提前警告（預設 3 分鐘，設定頁可改）期間顯示倒數
  （數字等寬，分鐘依這一題的警告長度補位，例如警告 10 分鐘時 10:00 之後是 09:59；倒數每秒換字時瀏海長度不變，FR-03）；
  已到期但被 guard 延後時直接說是什麼擋住，例如「時間到了，分享螢幕結束就跳出來」（2026-10-09 Ray 核准；完整對照見「守門」一節）；
  已經在問（蓋板或主視窗正在顯示這題）時只顯示一般待處理文字，不說「時間到了」；進入倒數時文字準時出現
  （2026-10-08 Ray：拿掉外側的倒數引信，靜止時只有圖示與文字）。文字沿瀏海
  排列，直向段由上往下讀、中文直立，轉角沿小圓弧轉彎並微微傾斜。
- **Hover：** 沿尾端稍微延長（圖示那一端永遠不動；尾端到角落的空間不夠時，尾端轉過角落延伸成 L 形），文字變成跑馬燈，輪播每題一句話摘要（去掉
  Markdown 符號與 HTML 標籤的純文字，但 `CPA<200` 這種比較符號與網址照原文；金額、百分比、時間、網址片段不被拆開；
  doctor 測試題等 internal 題不算題數、也不播）。分享螢幕、錄影、會議或全螢幕
  展示時不播題目內容：每次 hover 先確認最新的隱私狀態，確認前只顯示狀態文字；hover 中狀態改變立即生效。
  已知限制：macOS 沒有公開方法偵測別的 app 正在錄影或用 ScreenCaptureKit 分享畫面，所以只開螢幕錄影、
  沒開攝影機或麥克風、也不是前景全螢幕時偵測不到；需要錄影時請先開勿擾（瀏海會完全消失）。
- **點擊：** 直接進入完整決策介面，轉場從圖示中心展開。
- **不擋路：** 瀏海以外的區域（包含 L 形內側與選單列）完全不攔截點擊；看得到的黑色就點得到，看不到的
  地方不攔截；沒畫出瀏海時整個畫面都不攔截。在瀏海上按住後，放開前都算在拖曳瀏海，快速拖離也不會漏給下方的 app；拖曳中瀏海因勿擾或題目全部結案而消失時，這次拖曳就結束，之後瀏海再出現也不會攔截別的 app 的拖曳。瀏海不搶鍵盤焦點：已顯示時重新對帳不會再把它帶到前景，正在作答的蓋板不會失去輸入焦點。
- **減少動態：** 系統或 app 內的「減少動態」一改就生效，不需要重開。

可操作參考：`docs/prototypes/edge-notch.html`（2026-10-08 Ray 認可的效果）。

## 20. 回答延續原對話（Target）

### 20.1 問題

Claude 每天排程復盤廣告，卡住時用 Kunsu 問使用者；使用者回答後，Kunsu 目前只能開一段新的 `claude -p`
或 `codex exec` 對話處理答案。原本那段在 Claude App／Codex App 裡的對話停在原地，使用者看不到後續，
上下文也斷了。

### 20.2 產品承諾

使用者的回答優先回到**發問的那段對話**，讓它在 Claude App／Codex App 裡接著做，處理結果與 AI 回饋再交代
回 Kunsu。交付階梯：

1. **原對話正在等：** 建題後在背景掛著等待（Claude 用 background Bash 執行 `kunsu wait`），答案一到直接
   交給它，原對話在同一段對話中被喚醒繼續。
2. **原對話已結束：** 在同一段對話背景追加一輪（Claude `--resume`、Codex `exec resume`），使用者之後打開
   原對話就看得到；回執提供「打開原對話」。
3. **原對話仍被開著但沒在等：** 不搶寫（會分岔或被鎖），等它空下來再追加。
4. **都不可能：** 才開新對話處理，並附原對話連結與原因。

同一個答案只會走一條路徑。agent 處理完以 `ask_report` 回報結果與回饋；`ask_report` 不能作答或改答案。
錢類題不論走哪條路徑，執行仍只能經 Kunsu 的 UI 簽章鏈。

### 20.3 界外

- 透過跨 session 訊息 socket 喚醒閒置對話：需保存 session 秘密，另案評估。
- 在桌面 Kunsu 內顯示或延續對話內容：仍是紅線，對話留在 Claude／Codex。手機 App 可以顯示與接續對話（§30），對話真相仍由 Claude／Codex 保存。

## 21. 排程督導（Current，2026-10-08 實作，待 QA）

使用者想讓 AI 督促長期承諾，例如每天寫日記、每週檢討目標並想清楚怎麼達成。

- **排程不在 Kunsu：** 由使用者在 Claude Routines 或 Codex automations 設定；Kunsu 不新增任何排程時鐘。
- **系統認得排程呼叫：** 排程執行時以 `kunsu ask --routine …` 建題，Kunsu 保存排程身分（id、名稱、主機、
  觸發類型、宣告頻率）。
- **一樣逃不掉：** check-in 走同一個 15 分鐘強制循環與 guards。
- **AI 回饋：** 回答回到那次排程的對話（§20），agent 完成工作後以 `ask_report` 回傳回饋。
- **督導頁：** 主 app 依排程分組，列出每次 check-in 的時間、題目、使用者的回答、AI 回饋與狀態；未回應也
  照列。使用者按「這題不該問我」推掉的 check-in 標「退回」，不和 agent 取消混在「已取消」，近 30 天另計退回次數
  （2026-10-09 Ray 核准：督導要看得出是在面對還是在推掉）。超過宣告頻率兩倍沒報到時，在督導頁標示「排程可能沒在跑」，提醒使用者去檢查排程設定（只在 app
  內標示，不推播）。
- **不是聊天：** 歷史頁沒有回覆框；要追問就打開原對話。目標正本留在 vault 或排程 prompt。

## 22. 強制蓋板呈現可靠性與來源圖示（Target，P0 修復）

### 22.1 已確認的問題

1. 蓋板有時上半部超出螢幕、下方約 28% 沒蓋到，且蓋住選單列導致無法操作。根因：shell 先設位置再設
   大小，macOS 以左下角為錨長高；啟動後第一次開蓋板必錯。
2. app 啟動時若已有逾時題，蓋板只剩模糊背景、沒有內容、Esc 無效。根因：轉場事件在蓋板網頁開始監聽前
   送出而遺失，之後又永不重送。

### 22.2 產品要求

- 蓋板顯示前一次設定為目標螢幕的完整範圍，多螢幕與混合倍率下都精準覆蓋；螢幕重排後重新對齊。
- 蓋板只有在題目、輸入與關閉都已可操作時才出現；1.5 秒內未就緒就不顯示，改開主視窗聚焦該題，題目
  維持強制資格。
- Esc 與關閉在任何狀態下有效；網頁無回應時由原生層完成同一個關閉流程。
- 啟動時已有逾時題，必須在數秒內出現正確、完整、可關閉的蓋板。
- 在蓋板裡答完最後一題時，蓋板不會自己消失：回執留在畫面上，直到使用者按「完成」或 Esc（§23）。「保留回執」只在面板
  正顯示這次在面板裡送出的那張回執時成立；題目全部由其他通道結案、面板也沒在顯示這種回執時，蓋板自動收起。被其他
  通道結案的題在面板裡就地標成已結案，不能再作答。
- 「稍後再問」失敗時面板不收起，顯示看得懂的錯誤，可以再試；網頁只在 dismissal 成功後才告訴原生「Esc 已處理」，
  所以 Esc 失敗時原生 2 秒後備照樣完成，不會卡住。同一次蓋板裡每題只記一次 dismissal：重試只補還沒成功的，原生後備
  跳過網頁已處理的題（2026-10-09 QA 第 3 輪）。
- 沒有點擊位置時（題目自動到期、從選單列開啟），蓋板從瀏海最後回報的圖示位置展開，不再從左上角。

### 22.3 驗收

見 `docs/bdd/overlay-presentation.md`（AC-OP-01～11）。

### 22.4 來源圖示

Claude 題使用官方星芒輪廓（取自本機 Claude App 內的 AppLogo 向量），Codex 題使用花瓣雲加 `>_` 輪廓；蓋板
粒子、靜態 fallback、邊緣瀏海與主 app 標記同源。`visual_symbol` 仍可覆寫蓋板粒子圖形。

## 23. 決策面板改版（Target）

Ray 的回饋：AI 每天丟一堆文字與數字，真正重要的才會認真看；要看圖表與數據、要看 AI 為什麼問；舊版送出鍵
藏在輸入框裡、最底下右邊卻是「這題不該問我」，按鈕位置誤導。

- **證據｜決定：** 左欄是「為什麼問你」與證據（圖表、表格、素材圖），右欄只放這一題的決定；沒有證據時
  改成置中單欄。
- **按鈕：** 右下角只有「送出決定」，未準備好時停用；「稍後再問」在右上角並寫明「N 分鐘後再問」（N 是目前生效的強制
  週期長度，預設 15；2026-10-09 起跟著設定頁的週期，不再寫死）；「這題不該問我」降為左下角次要文字。從歷史紀錄回看已結案的題
  沒有「稍後再問」，右上角改成「關閉」。
- **選項：** 點選只選取、不誤送；可加補充說明一起送出（答案同時保存選項與文字）。
- **轉場：** 瀏海先沿邊延伸、再往內展開成面板；來源圖示飛到頁首；收起倒放。取代墨水擴散與左側大型粒子圖像。
- **脈絡：** 時間軸呈現 AI 做了哪些步驟、為什麼卡住；可打開原對話、看 AI 送來的原文。
- **不顯示倒數（2026-10-09 Ray）：** 面板開在你面前時，「幾分鐘後強制詢問」沒有意義；15 分鐘週期只在背景計算。
  頁首右側只有「稍後再問」。瀏海靜止時最後 3 分鐘的「m:ss 後強制詢問」照常（那是面板還沒打開時的提醒）。
- **QA 第 1 輪修正（2026-10-09）：** 回執一定看得到（蓋板裡最後一題也一樣，按「完成」或 Esc 才收起）；焦點在選項上按
  Enter 送出目前的選取、不會改選；張開動畫中不會誤點，但 Esc 從第一刻就有效；主視窗等窄畫面（寬度 < 1100 px）改單欄
  整體捲動、操作列固定在底部；尊重 Kunsu 自己的「連續轉場動畫」設定；沒有選項的確認題按「確認」就能作答。

- **格式：** 文字、表格、圖片用 Markdown；需要圖表或任何視覺化時，AI 寫一個 React（或 HTML）畫布，可用

## 25. 題組與更多題型（題組已實作，待 QA；其他題型 Target；2026-10-09 Ray 核准）

### 25.1 為什麼

Kunsu 現在一題只能問一件事。AI 一次處理一批同類工作時（例如 10 封回信草稿），只能拆成 10 題，使用者要開關 10 次、
來回 10 輪，效率很差，也容易因為累而亂答。題組讓使用者在**同一個面板**一次看完、改完、決定完一批項目，AI 再照
確認過的內容逐項執行。

### 25.2 題組（`kind = batch`；2026-10-09 實作，待 QA）

- **一題多項：** 一題放 1–20 個同類項目。每項有標題（例如寄件人＋主旨）、原文脈絡（來信全文、留言串、申請內容）、
  AI 的建議（草稿文字，或「照規則核准／婉拒」的建議）。
- **兩種項目：** 可編輯的（回信、留言回覆、文案，使用者可以直接改草稿），以及只核可的（退款、報帳分類、要不要隱藏
  留言，沒有草稿框，不能改文字）。兩種項目都有三個決定鈕：只核可的項目是「照建議」「不處理」「請 AI 改」（2026-10-09
  依 Ray 核准的原型修正；舊文寫「只能照建議或不處理」與原型、DESIGN 不一致）。
- **不准佔位文字（2026-10-09 Ray）：** AI 建議不處理的可編輯項目，草稿要嘛是空的，要嘛是真的可以送出的回覆，不准寫
  「（不回）」之類的佔位文字（原因寫在 `default_reason`）。可編輯項目採用時最終文字不能是空的：面板停用送出並寫
  「第 N 項沒有內容，先寫好再採用」，server 也拒收。
- **題組只能在面板逐項作答：** 題組不能帶 `kongko_ref`（Kongko 發佈事件沒有逐項決定，不能結案題組），建題時就拒收。
- **輪次 id：** 第 2 輪以後的題組 id 是 `<原 id>-r2`、`-r3`…；題組 id（不含輪次後綴）最多 116 字，留出輪次後綴的空間
  （題目 id 上限 120 字），建題時就檢查。
- **每項三種決定：** 採用（可先改再採用）、不處理、請 AI 改（附一句怎麼改）。預設是採用；AI 認為不該回的項目
  （例如促銷信、情緒性留言）預設不處理並寫明原因。使用者只需要處理例外，一鍵送出。
- **一鍵處理全部：** 「全部採用 AI 草稿」；「全部退回，請 AI 重寫…」附一段給 AI 的指示，套用到所有項目。
- **所見即所送：** 使用者確認的文字就是 AI 要送出的文字，一字不改；答案綁定項目版本與內容雜湊，ledger 可追溯。
- **改稿迴圈：** 有項目「請 AI 改」或全部退回時，這一題照樣結案（已採用的照常執行），AI 依指示改好後以「第 2 輪」
  新題組送來，只含要重看的項目，並標明是哪一題的第幾輪。
- **畫面：** 左欄跟著目前選中的項目顯示原文；右欄是項目清單（每項一張卡：標題、狀態、一行摘要、草稿輸入框、
  三個決定鈕），最上面是兩個一鍵按鈕，最下面是總結列（「採用 8 項 · 其中 1 項你改過 · 不處理 1 · 請 AI 改 1」；
  Kunsu 不知道一項是信還是留言，所以用「採用／項」而不是「寄出／封」）
  與送出。鍵盤：J／K 換項目、E 編輯、A 採用、X 不處理、R 請 AI 改、⌘Enter 送出。
- **界外：** 題組裡不能放動錢的項目（錢題仍一題一題走授權鏈）；Kunsu 不代寄信、不代發文，執行是發問的 AI 的事。

### 25.3 其他題型（構想，依價值排序）

|---|---|---|
| 題組（上面） | 回信、Threads／IG 留言回覆、客服回覆、廣告文案變體、退款／報帳逐項核可 | 先做：最常見、省最多時間 |

### 27.3 設定要能改的東西

設定改的是使用者個人的值，存在 `~/.kunsu/policy.local.toml`（安裝不會覆蓋），覆寫 repo 的 `config/policy.toml` 預設值；
存下立即生效，不用重開 app。每一項都顯示目前值、預設值與「回復預設」。

- **睡眠時間（安靜時段）：** 開關＋開始／結束時間（台北時間，可跨午夜）。期間不強制詢問、不發提醒；題目與週期照常保存，
  結束後依原進度恢復（與 guard 相同語意）。
- **強制詢問：** 週期長度（5–120 分鐘，預設 15）、提前警告（1 分鐘到週期長度減 1，預設 3）。只影響之後新開始的週期，
  已經在跑的週期照原本時間。
- **到期與配額：** 一般題沒回答多久後到期（1–336 小時，預設 48）、題目最長等待天數（所有題目，1–14 天，預設 14；策略題到期由
  新題取代，其他題到期結案；上限 14 天是不變量）、每個來源每天最多建幾題（1–100，預設 12）。**到期規則在建題時固定在題目上**

  到期、更不會依預設選項替使用者作答。
- **疲勞降級：** 觀察幾天（1–30，預設 7）、略過率超過多少就降級（10%–100%，預設 50%）。
- **外觀與動態：** 主題（跟隨系統／淺色／深色）、連續轉場動畫（同既有開關）。
- **勿擾：** 目前狀態、快捷時長、自訂時長、提前結束（同既有控制，換新外觀）。
- **瀏海：** 回到預設位置。
- **Agent 連線：** 真實狀態（Claude MCP 註冊、Codex MCP 註冊、`kunsu` CLI、kunsu skill），未設定時給可複製的設定指令；
  不再有假的「連接／中斷」按鈕。
- **資料與帳本：** vault 與資料庫位置、帳本健康（待補寫行數、OPEN.json 待重寫、寫入卡住秒數），有問題時說明怎麼修並提供

## 28. 私人助理草稿收件匣（Current，2026-10-10）

每天巡檢課程、Meta（含私人訊息）、Threads 與 LINE；AI 自行查證並提供一份最佳草稿。右欄一次看完、直接編輯，左欄精簡來源與原文。沿用 batch，支援 1–20 項，單項也保留可編輯草稿。來源用 subtitle 的固定前綴「課程｜」「Facebook｜」「Instagram｜」「Threads｜」「LINE｜」，後接帳號與收件者；context_md 保留來源連結與原文，不能由名稱猜平台。

頂部呈現來源圖示與件數；點分類定位到第一則，不隱藏其他會送出的項目。「確認」是可撤銷的已看過註記，不產生正式答案，也不是全部送出的前提。編輯或 AI 更新內容會清除該註記。「請 AI 改」附指示，送出後只重擬該項，新提案回來再看。改稿與決定保存於本機，關閉／重開恢復，不能以 AI 重送覆蓋使用者的修改。

唯一對外發送授權是使用者明確按「全部送出 N 則」或相應鍵盤操作所產生的正式 batch 答案。文字按畫面現值傳回 AI；略過與重擬項目不寄送。不需逐則按確認。顯示總件數及「你按下全部送出後，助理才會依目前文字發送」。排程、逾期、預設採用、已看過與關閉視窗都不能授權發送。草稿建立後回原對話執行，Kunsu 本身不直接串各平台。

## 29. Codex 對話鎖與已回答補查（Current；宿主接收待端到端驗證，2026-10-10）

Codex `exec resume` 遇到 active writer 時，使用同一受信任 CLI 的 `queue --thread --message` 將簡短的 question_id / answer_id 指示排入原對話，不攜帶原始對話、不改模型／權限、不搶鎖。只有 CLI 明確回覆該 thread 已排入才停止重送；UI 寫「已排入原對話，等待 AI 接手」，不稱完成。舊 CLI 不支援則保留 held。

客服每輪優先補查全部已知題目（含更早輪次）：正式答案是批准，delivery 是通知，逐項 execution 是實際結果，ask_report 是批次回報，四者分開。完成前先寫 sending，確認站內結果後才 sent；sending/unknown 先核對平台，不能盲目重送。只有所有項目處理與回報都完成才結案。

## 30. 手機 App（Target，2026-10-10 Ray 核准；Prototype 階段）

### 30.1 問題與真正目標

使用者躺在床上時，AI 卡在等他。現在只能起床開電腦，或者讓 agent 一直停著。目標是讓使用者 **用手機在最少步驟內
讓 AI 繼續工作**：回答 Kunsu 決策題、回覆正在等他的對話、批准權限，必要時開新對話。這原本是作者自用的工具，
以好用為準，不以商業規模為準。

### 30.2 紅線後退（2026-10-10 Ray 核准）

- 手機 App 可以檢視、接續與建立 Claude Code／Codex 的桌面對話；桌面 Kunsu 仍然不做聊天介面。
- 允許一台 Zeabur 中轉站，但它只轉送端對端加密封包、發送無內容推播；不保存可讀的對話、題目、答案或金鑰。
- 不變：Kunsu 不代答、不代授權；決策題只能用決策卡作答（聊天訊息不會變成正式答案）；錢只走簽章鏈，手機上先跳出核對畫面（所見即所簽）再批准，
  不另外要求 Face ID（2026-10-12 Ray 決定）；真相留在 Claude／Codex 與 Mac 上的 Kunsu。

### 30.3 產品形狀

原生 iPhone App（SwiftUI），提供淺色與深色模式，預設跟隨系統（2026-10-12 Ray 要求；網頁 Prototype 同樣兩種都要）。一條導覽堆疊，沒有分頁列：

1. **首頁「等你」**：依「誰卡在你身上」排序，不依時間：要你決定（Kunsu 題）→ 等你回話／等你批准的對話 →
   執行中 → 最近。頂端永遠顯示 Mac 連線狀態；Mac 連不到時寫「Mac 離線 · 最後同步 HH:MM」，不能顯示成「沒有事」。
2. **對話頁**：Claude 與 Codex 用同一種畫法，只差來源標記。工具呼叫收成一行摘要（「改了 3 個檔 · 跑了測試 ✓」）。
   權限請求是行內卡片（允許一次／拒絕）。這段對話有待決 Kunsu 題時，題目以決策卡釘在輸入列上方。輸入列提供
   「繼續」快速回覆、從 AI 最後一則訊息抽出的選項、語音輸入。
3. **對話流（A/B 評估中，2026-10-10）**：把首頁換成「軍師跟你的一條對話」。所有在等你的東西排在最下面、貼著唯一的
   輸入框，處理完的往上變成歷史；輸入框上方永遠寫出回覆對象，預設是最下面那一則可打字回覆的對話，點卡片就換對象，
   不由 AI 猜你在回誰。決策題與權限請求在流裡仍是卡片，用按鈕回答；開新對話也從同一個輸入框切換對象開始。
   Prototype 同時保留清單版，用 K 圖示切換，使用者實際使用後再擇一。
4. **決策卡**：桌面決策面板的手機版，作答規則與桌面相同（§23、§25）。
5. **新對話**：選 Claude／Codex（記住上次）、最近專案、權限模式（預設 Auto：Claude 用 auto mode、Codex 用 auto 預設，安全的動作自己做，高風險的才跳回手機批准；另可選「會問我」；不提供繞過權限。2026-10-10 Ray 核准），第一句可語音。

### 30.4 快速回覆原則

- 簡單單選題可在鎖定畫面通知直接作答（2 下）；打開 App 作答不超過 3 下。錢一律打開 App 的核對畫面再批准；不使用 Face ID（2026-10-12 Ray 決定：多一次刷臉沒有必要）。
- 不用滑動手勢作答；所有決定是點擊確認。主要按鈕在拇指可及的下半部。
- 非錢的送出有 5 秒「撤回」窗；撤回前不送到 Mac。
- 回答後顯示與桌面相同語言的交付回執（§20、§29）。

### 30.5 架構與安全（Target）

```
iPhone ⇄ Zeabur 中轉站（只轉加密封包、發 APNs） ⇄ Mac 橋接（主動往外連，不開對外 port）
       ⇄ codex app-server ／ claude --bg、stream-json
```

- 配對：Mac 顯示 QR code，手機掃描交換金鑰；手機私鑰在 Secure Enclave，可在 Mac 端撤銷裝置。
- 推播：APNs payload 為加密內容，由手機的 Notification Service Extension 解密後才顯示題目與按鈕；Apple 與 Zeabur 看不到內容。
- 指令範圍：手機只能送「訊息、回答、權限批准／拒絕、開新對話、停止」，不能直接執行 shell。
- 正在桌面上執行的對話：Codex 走共用 app-server，不另開分岔；Claude 若只能另開副本，手機上該對話改為唯讀加排隊，
  不得靜默分岔（待技術驗證）。

### 30.6 目前階段與未驗證

- **已完成（2026-10-12）**：SwiftUI App 以統一設計語言重寫；掃 QR 配對、經 Zeabur 中轉站端對端加密、在手機上作答（含動錢核對）已在模擬器經真實中轉站端對端驗證，並安裝到 Alex 的 iPhone。
- **已完成（2026-10-12，第二批）**：中轉 AI 工作階段（追問、答完聊天）、問本人（`ask_followup_reply`）、從手機開新任務（CONTRACT §17）；
  在模擬器經真實中轉站與真的 Claude 端對端驗證（追問、問本人、聊天、在暫存專案開新任務並真的建出檔案）。順手修掉：動錢題選「維持」
  沒過核對畫面而被 Mac 拒收、手機卻顯示已交出；重開 App 手機換身分；主畫面圖示空白。
- **下一階段**：等你回話與權限批准的對話控制、APNs 推播（需要付費 Apple Developer 帳號與 .p8 金鑰）。這些在手機上會清楚寫「下一版」。
- **未驗證**：從外部接上 `codex app-server` 是否與 Codex 桌面 App 同步；`claude --bg --resume` 對正在跑的對話是否分岔；
  Zeabur WebSocket 長連線穩定度；APNs 需要 Apple Developer 帳號（年費，待 Ray 同意付款）。
- BDD 在 Prototype 確認後撰寫（`docs/bdd/mobile-app.md`）。

### 30.7 中轉 AI、追問與答完後的聊天（Target，2026-10-12 Ray 要求）

- **中轉 AI**：Mac 上一段專屬的 Claude 或 Codex 工作階段，代表「軍師」跟使用者對話。用哪一個在手機設定與主視窗「設定」都能選，
  兩邊是同一個值，存在 Mac。
- **追問**：決定題與批准題上的「為什麼？」「前因後果？」和打字，都是追問，不是答案，也不改倒數。中轉 AI 先答：它讀得到題目的
  脈絡、證據與原對話最後幾段（唯讀）。答不了時使用者可以按「問 <專案> 本人」，Kunsu 把追問交給正在等這題的原 AI：`ask_wait`
  除了答案也會回 `followup` 事件，原 AI 用新 MCP 工具 `ask_followup_reply` 回答後繼續等。原 AI 沒在等時只能由中轉 AI 答，畫面寫清楚。
- **打字的去向**：等你回話的題，打字就是回覆原對話；決定題與批准題，打字是追問（取代桌面的「補充說明」）。
- **答完後的聊天**：沒有事在等使用者時，輸入框直接跟中轉 AI 聊天：問各 AI 的進度、開新任務（它會問哪個專案）、把話轉給某段對話。
  中轉 AI 永遠不能作答決定題、批准指令或批准動錢；聊天中有新題進來，以問題卡插入，答完回到聊天。
- **桌面不聊天**：主視窗只有「中轉 AI」設定；聊天只在手機（§14 紅線仍適用桌面）。
- **階段**：先做手機介面（模擬資料，與 Mac 上 Kunsu 的連線層抽象成一個介面），再做 Kunsu 核心的手機作答通道、追問 MCP 與
  中轉 AI 工作階段，最後才是 Zeabur 中轉站與推播（需 Ray 同意部署與付 Apple Developer 年費）。

### 30.8 配對與手機作答通道（Target，2026-10-12 Ray 決定）

- **答案來源改成「使用者本人的通道」**：拿掉封閉白名單（UI IPC／kongko／Discord／CLI），改為使用者本人的通道都可以作答：電腦介面、
  已配對的手機、Discord 讀回、終端機 CLI、Kongko 發佈。唯一保留的禁令：**AI agent 用的 MCP 工具永遠不能作答或批准**——否則 AI 能
  自己回答自己的問題（違反 §1.4 永不代答）。手機作答不走 MCP，所以不受影響。
- **動錢**：電腦介面或已配對手機都能批准；手機上一定先經過核對畫面（所見即所簽），沒有 Face ID。其他通道仍不能批准動錢。
- **配對**：主視窗「設定 → 手機」按「配對新手機」顯示 QR code（中轉站網址、Mac 公鑰、5 分鐘一次性配對碼）。手機第一次打開就是掃描
  畫面。手機把配對請求加密送到 Mac 後，**主視窗跳出「<裝置名稱> 要配對 → 允許／拒絕」，使用者在電腦上按允許才成立**；QR 被拍走也配不上。
  主視窗列出已配對裝置，可隨時撤銷。
- **傳輸**：經使用者自己的 Zeabur 中轉站。中轉站只轉送密文、不落地、Mac 離線時最多在記憶體暫存 10 分鐘。手機與 Mac 之間端對端加密；
  手機每個請求以裝置私鑰簽章（私鑰在 Secure Enclave，不可匯出）；Mac 拒絕簽章錯、裝置已撤銷、重放、時間差超過 120 秒的請求。
  協定細節：`docs/design/mobile-relay.md`。
- **推播**：下一步（需要 APNs 金鑰）；推播內容同樣加密，Apple 與 Zeabur 看不到題目。

## 31. 公開產品：多使用者、上架與開源（Target，2026-10-13 Ray 決定）

### 31.1 方向改變

Ray 決定把 Kunsu 從「作者自用」改成**公開給所有用 AI Agent 工作的人的產品**：上架 App Store、做官網與銷售頁、開放註冊、
程式碼與文件全部開源。下面這些承諾**不變**，而且是公開版的主要賣點：

- **內容只在使用者自己的電腦上。** 題目、答案、證據、對話、草稿、帳本，全部只存在使用者的 Mac；雲端永遠拿不到。
- **中轉站只轉密文。** 手機與 Mac 端對端加密，中轉站與 Apple 看不到內容（§30.8、INV-30）。
- **不代答、不代授權、不自動執行**（§1.4、INV-7）；動錢只走簽章鏈。
- 一般 FYI、進度與成功通知不進 Kunsu。

### 31.2 帳號：雲端只存帳號基本資料

- **存什麼**：email、顯示名稱、登入方式、建立時間；這個帳號的 Mac 與手機清單（裝置 id、名稱、公鑰、配對與最後上線時間），
  以及中轉站連線憑證。只為了登入、裝置管理與中轉站路由。
- **永遠不存**：題目、選項、答案、證據、對話內容、AI 回饋、帳本、草稿、檔案路徑，以及任何可以拼回這些內容的東西。
- **登入**（2026-10-13 Ray 決定）：三種，不做密碼——
  - **Email 一次性登入連結**（magic link），用 Resend 寄送，寄件網域 kunsu.app；連結 15 分鐘有效、只能用一次。
  - **Google 登入**（OAuth）。
  - **Apple 登入**（Sign in with Apple；App Store 規定有 Google 登入就必須提供）。
  同一個 email 用不同方式登入是同一個帳號。
- **刪除帳號**：App 與網站都能刪除帳號（App Store 規定 5.1.1(v)），刪除後雲端資料 30 天內清除；使用者 Mac 上的資料不受影響。
- **配對**：維持 QR＋Mac 上按允許（§30.8、INV-29）。帳號只是讓同一個人的裝置找得到彼此的中轉站通道，不取代 Mac 上的允許。
- **中轉站**：從「一台 Mac 一個 RELAY_MAC_TOKEN」改成「每個帳號、每台 Mac 一組憑證」，多租戶，仍然不落地、不解密。

### 31.3 去個人化：陌生人裝得起來

目前電腦版綁著作者個人的環境。公開前要改成：

- vault 根目錄、帳本位置改成首次設定時選（預設 `~/Kunsu`），不再寫死作者的個人資料夾。
- Meta 廣告執行器（動錢鏈）、Kongko、Discord 告警、私人助理草稿收件匣改成**可選整合**，預設關閉，有設定才出現。
- 首次設定流程：登入 → 選資料夾 → 安裝 Claude Code／Codex 外掛 → 配對手機 → 送一題測試題。
- 手機與網站上的「晚安」等寫死的名字改用帳號的顯示名稱。

### 31.4 發佈管道

- **Mac**：Developer ID 簽章＋Apple 公證的 DMG，內建自動更新；官網直接下載。
- **iPhone**：App Store（先 TestFlight）。
- **Agent 端**：Claude Code 外掛目錄、Codex 外掛；README 一行安裝。

### 31.5 開源

- 程式碼、文件（PRD、DESIGN、CONTRACT、BDD、INVARIANTS）、設計稿全部公開，授權 MIT（2026-10-13 Ray 確認）。
- 公開前：清掉所有個人資料（作者的路徑、帳號、廣告帳戶 id、vault 內容引用、測試資料裡的真實內容），用**一份乾淨的新歷史**開公開
  repo；現在的 552 筆歷史不公開。公開前由作者逐項確認。
- 「數據開源」的範圍待 Ray 確認：是否也公開營運數據（例如下載數、活躍數的公開儀表板）。使用者的資料永遠不公開，也不在雲端。

### 31.6 官網 kunsu.app

- 網域 kunsu.app 在 Cloudflare 註冊與管 DNS；網站託管在 Zeabur。購買由作者當下確認金額後才執行。
- 銷售頁參考 dub.co 的質感：首屏可以直接註冊與下載；整頁用可互動的產品示範說服，包含可操作的主視窗側欄、可以拖的邊緣瀏海
  （通知）、手機 App 的一問一答動畫。動畫是加分項：減少動態時有靜態版本，手機版版面完整。
- 從看到、被說服到註冊：首屏（一句話＋註冊＋下載）→ 問題（AI 卡在等你）→ 互動示範 → 隱私（內容不離開你的 Mac、開源可查）→
  安裝三步驟 → 常見問題 → 再一次註冊。
- 必要頁面：隱私權政策、服務條款、支援、開源連結（App Store 審查需要隱私權政策與支援網址）。

### 31.7 App Store 過審清單

- 審查員連不到使用者的 Mac：App 內有清楚的「示範模式」，審查備註附示範影片與步驟；必要時提供一台審查用的示範 Mac 帳號。
- App 圖示用 asset catalog 編譯（需要安裝與 SDK 對應的 iOS 模擬器元件）。
- 隱私：PrivacyInfo.xcprivacy（UserDefaults 等需要說明理由的 API）、隱私營養標籤（只有帳號 email／名稱，用於 App 功能，不追蹤）、
  隱私權政策網址、支援網址。
- 帳號：提供 App 內刪除帳號；提供 Sign in with Apple。
- 加密：只用標準演算法（CryptoKit、ChaCha20-Poly1305、X25519、P-256），出口管制申報屬豁免，照實填寫。
- 清掉測試用按鈕（「模擬重新打開 App」）與「下一版」字樣；所有按鈕都要有實際功能。
- 名稱：上架前查「Kunsu」「軍師」商標。
